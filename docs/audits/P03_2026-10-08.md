## 1. Data and database: no defects found

**Evidence:** `supabase/migrations/001_registrations.sql`, `api/_lib/db.ts`, `shared/registration.ts`, `apps-script/Code.gs`, plus 11 PGlite tests running the real SQL.

| Check | Result |
|---|---|
| Schema vs code | `toPayload()` output = `RegisterPayload` = the `register_attendee` JSON fields. `sheet_pending` columns = Sheet headers minus `synced_at`. **No mismatches.** |
| Migrations tracked | Yes: an up/down pair, with the round trip tested in PGlite. **Drift risk:** LIVE isn't migrated yet, and there's no migrations table, so a dashboard edit would go unrecorded. The rule stays: SQL changes only via files, TEST then LIVE (CLAUDE.md). |
| Constraints in the DB, not just the UI | Yes: phone format, lowercase email, code alphabet, gender, lengths, `age_confirmed = true`, statuses, UNIQUE (event, phone/email/code). The DB is deliberately looser than zod on `department`/`institution` (UI-only rules); that's acceptable. |
| Indexes | Duplicate lookup is covered by the two unique indexes (OR → bitmap). Retry by `(event, email_status)`. Sync by a partial index on unsynced rows. Mark-synced uses the PK. **None missing.** |
| Orphans and cascades | Only one table today. **Decide in M6:** the FK behaviour of `winners.registration_id` when a registration is deleted on request (recommended: `ON DELETE CASCADE`, since a deleted person can't win). |

## 2. Business logic

| Check | Result |
|---|---|
| Hardcoded values | Event content is centralised in `shared/event.ts` (by design). Throttle (10 min), retry cap (5) and batch sizes live in SQL and constants. They're fine for one event, and changing them is a code change, not an admin setting. **Acceptable.** |
| Status lifecycle | `email_status`: PENDING → SENT / FAILED / LOGGED; FAILED → retried up to 5 times; stale PENDING (>10 min) retried. **Gap:** a row that exhausts 5 attempts stays FAILED silently (see P03-01). **Gap:** `LOGGED` in production would never be retried (P03-03). |
| Concurrency | Registration: atomic via constraints and the retry loop; proven with 50 parallel requests plus a same-instant race (M1). **Gap:** `email_retry_batch` doesn't claim rows, so two overlapping retry runs could double-send (P03-05). |
| Dates and time | `timestamptz` everywhere (UTC), converted to Africa/Lagos only for the Sheet. The open/close window (M4) must use ISO strings with an offset (already in `.env.example`). |

## 4. Reliability and operations

| Check | Result |
|---|---|
| Error tracking | **None beyond Vercel function logs**, and Hobby keeps runtime logs only briefly (verify the retention). Nothing tells the builder that emails are failing, the Sheet has stopped syncing, or registrations are erroring. **P03-01 (High).** |
| Personal data in logs | API logs carry only the row `id`, timings and outcomes. **Exception:** SMTP error text can include the recipient address (e.g. `550 <x@y> unknown user`) (P03-06). |
| Dev/prod separation | Good: separate Supabase projects and Sheets; Preview → TEST; Production has no env yet. |
| Backups | The Supabase Free plan's backup and restore options are **unverified**. The Sheet mirror is a live second copy, but a restore has never been tested (P03-08). |
| Timeouts and degradation | DB: 10s timeout. Email: send-after-response plus retry. Sheet failure doesn't affect registration. **Gap:** nodemailer has **no timeouts set**, so its defaults apply (connection about 2 min, socket about 10 min). A hung SMTP connection would hold a function until `maxDuration` and stall a whole retry batch (P03-02). |
| Env vars documented | `.env.example` is complete for the app. Apps Script properties are documented in `Code.gs`. |
| Rollback | App: Vercel "Promote" of the previous deployment (instant). DB: `.down.sql` (destructive; export first). **Write this into the admin guide (M5).** |
