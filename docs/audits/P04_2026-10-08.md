## Threat model

**Assets:**
- Students' personal data: names, phones, emails, gender, home addresses (NDPA)
- Raffle integrity: one fair ticket per person
- The church Gmail: its app password can read and send mail
- The Supabase secret key: full database access
- Uptime during outreach

**Realistic attackers:**
- Spam bots on a public form
- A student trying to win: extra tickets, someone else's code
- A curious person poking at the API
- Someone with editor access to the Sheet

**Attack surface:**

| Entry point | Who can reach it | Protection |
|---|---|---|
| `/` and `/privacy` (static, pre-rendered) | Public | No user data rendered |
| `POST /api/register` | Public | zod server validation, window check, honeypot plus timing, unique constraints |
| `GET /api/status` | Public | Returns only open/closed state |
| `POST /api/email-retry` | Apps Script | `Bearer RETRY_SECRET`, timing-safe compare |
| `GET /api/health` | Public | Returns `{ok:true}` only |
| Supabase REST (`*.supabase.co/rest/v1`) | Public URL | RLS on with no policies; function EXECUTE revoked from anon/authenticated; **hosted check pending (S-05)** |
| Apps Script (no web app any more) | Sheet editors only | Secret key in Script Properties |
| Google Sheet | Named leads | Private sharing |
| Vercel preview deployments | Vercel team only | Deployment Protection; point at TEST |

N/A: auth/login, payments, AI, file uploads, storage buckets, webhooks, admin pages.

### Checked and fine (evidence)
- **Secrets:**
  - git history only contains test fakes (`sb_secret_x`)
  - `.env.local` was never committed (only `.env.example`)
  - the built `dist/` contains no `sb_secret`, `SMTP_PASS`, `RETRY_SECRET` or `supabase.co`
  - no `VITE_` secrets
- **Injection:** database access goes only through parameterised RPC (supabase-js `rpc()`), with no string-built SQL. React escapes output, and there's no `dangerouslySetInnerHTML`. Email values are HTML-escaped, and an unfilled placeholder throws. Sheet cells have the formula guard.
- **Server-side validation:** a zod schema on the server, plus database CHECK constraints.
- **Code harvesting:** duplicates never return the code (unit and e2e tested).
- **Same-instant double registration:** prevented by unique constraints (M1 race test).
- **CSRF:** N/A. There's no cookie or session; the only effect of a cross-site POST is a registration, which anyone can do directly. Cross-origin browser POSTs with a JSON body need a preflight, which gets no CORS headers.
- **CORS:** no `Access-Control-Allow-Origin` is set anywhere (no wildcard).
- **Errors and logs:** generic JSON errors; email addresses scrubbed from logs; no stack traces sent to clients (Vercel's 500 page shows only an id).
- **`/api/email-retry`:** a secret is required (unit tested). It only re-sends to addresses already on file.
- **Supply chain:** every dependency is established and maintained: react, zod, react-hook-form, @hookform/resolvers, lucide-react, nodemailer, @supabase/supabase-js, @vercel/functions; dev: vite, tailwindcss, vitest, oxlint, @playwright/test, @electric-sql/pglite, @react-email/*, tsx. No lookalike names.

### Manual checks (builder)
**1. On TEST now, and on LIVE after M5's migrations.** Supabase SQL editor; paste the output:
```sql
select tablename, rowsecurity from pg_tables where schemaname = 'public';
select * from pg_policies where schemaname = 'public';
select p.proname,
       has_function_privilege('anon', p.oid, 'execute') as anon_exec,
       has_function_privilege('authenticated', p.oid, 'execute') as auth_exec
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public';
select grantee, privilege_type from information_schema.role_table_grants
 where table_name = 'registrations' and grantee in ('anon', 'authenticated');
```
Expected:
- `registrations` has `rowsecurity = true`
- **no policies**
- every function shows `anon_exec = false` and `auth_exec = false`
- **no grants** to anon or authenticated
